# RT3D-001 — Real-time 3D foundation

Issue: #219
Branch: `agent/rt3d-001-realtime-foundation`

## Status

IMPLEMENTED — the interaction foundation and first in-app visual checkpoint are committed in this branch. Final visual handoff is not complete until the successful main commit is promoted into the retained root APK.

## Product checkpoint

CARGame is now architected toward a real-time interactive 3D runtime. New gameplay work must not extend the old flat/card presentation or treat pre-rendered WebP cargo as the final gameplay renderer.

The mandatory visual policy is defined in `docs/VISUAL_APK_CHECKPOINT_POLICY.md`: every user-facing increment, even a small one, must have a reachable visual representation and must ultimately be visible in `Last verified APK/CARGame-latest-verified.apk` after main verification/promotion.

## Implemented

- Pure-Dart 3D vector, ray, plane and AABB math.
- Stable cargo/entity and delivery-target domain contracts.
- Renderer-independent `Realtime3dScenePort`.
- `CargoDragController` with guarded `idle -> selecting -> dragging -> resolving` state machine.
- Screen-ray to world drag-plane projection.
- Render-only cargo lift while preserving logical drop surface coordinates.
- Compatible target snap, wrong-target return, miss return and explicit cancel.
- Target hover compatibility feedback contract.
- Anti-spam protection while asynchronous picking/resolution is active.
- Geometry and controller unit tests.
- Real-time scene, camera, lighting, performance, asset and migration architecture in `docs/REALTIME_3D_ARCHITECTURE.md`.
- Reachable `3D VISUAL LAB` route in the actual app shell.
- Perspective-projected 3D ground, roads, warehouse, delivery buildings and cargo.
- Visual cargo selection, compatible/wrong dock hover, snap/return motion, shadows and camera orbit.
- The lab reuses `CargoDragController` and `Realtime3dScenePort`; it is an interactive visual harness, not a disconnected mock or the final native renderer.

## Invariants preserved

- No persistence key changes.
- No economy/reward changes.
- No level generator changes.
- No move consumption changes.
- No existing 150-level truth changes.
- No renderer dependency is admitted in RT3D-001. The visual lab uses a Flutter-projected renderer adapter so the already-implemented 3D interaction can be inspected immediately without forcing a toolchain migration.

## Renderer dependency decision

The latest Thermion line currently requires Flutter beta/native-assets setup, while the repository is governed on the stable Flutter toolchain. RT3D-002 therefore owns any production renderer/toolchain admission decision. The app-visible RT3D-001 checkpoint remains renderer-independent and does not silently change the project SDK channel.
