# ENG-011 — Developer tooling and documentation

State: IN PROGRESS  
Issue: #173  
Branch: `agent/eng-011-developer-workflows`  
Started: 2026-08-10

## Goal

Make setup, daily development, Android execution, repair, dashboard access, CI-parity verification, and release packaging reproducible from a clean checkout through one canonical workflow that matches the repository's current architecture.

## Audit finding

The existing root README still contains obsolete bootstrap/release guidance from an earlier project state. In particular, it directs developers to regenerate Flutter scaffolding over the project, edit advertising IDs in tracked files, and add consent support manually. Current main already tracks Android/iOS project files, externalizes release AdMob/signing inputs, validates them through release preflight, and implements Google UMP through ADS-007.

## Implementation plan

- Add `docs/DEVELOPER_WORKFLOWS.md` as the canonical supported workflow.
- Rewrite `README.md` so quick start and release instructions delegate to the current scripts rather than historical setup steps.
- Define the supported Windows surfaces: `START_CARGAME_TOOL.bat`, `SETUP_TOOL.ps1`, `FIRST_TIME_SETUP_AND_RUN.ps1`, `RUN_ON_EMULATOR.ps1`, `REPAIR_ANDROID_BUILD.ps1`, `REPAIR_KOTLIN_CACHE_AND_BUILD.ps1`, `OPEN_DEVELOPMENT_DASHBOARD.ps1`, `VERIFY_RELEASE_INPUTS.ps1`, and `BUILD_RC.ps1`.
- Add an executable documentation/tooling contract that checks those entry points exist, verifies required current guidance, and rejects known stale/dangerous instructions or hard-coded emulator serials in the canonical docs.
- Add focused regressions and blocking Flutter CI gates.
- Reconcile `docs/FEATURE_CATALOG.md` and `docs/STATUS.md` after full verification.

## Acceptance

- One document contains clean checkout, first run, day-to-day run, emulator/device, repair, dashboard, verification, release, and troubleshooting paths.
- Canonical docs never tell a developer to regenerate the Flutter project over an existing checkout, paste production AdMob/signing values into tracked files, manually duplicate UMP integration, or hard-code an Android device serial.
- Release guidance uses `VERIFY_RELEASE_INPUTS.ps1` and `BUILD_RC.ps1` with production values kept external to source control.
- CI fails if a required supported entry point disappears or stale guidance returns.
- Existing privacy/security/dependency/catalog gates, Analyze, full Flutter tests, Debug APK, and artifact-security checks remain green.
