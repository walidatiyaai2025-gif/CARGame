## Architecture decision

Do not renumber or expand the gameplay archetype IDs as a visual-content shortcut. Add a separate visual identity layer:

1. gameplay archetype ID remains the matching/save/reward authority;
2. each archetype owns multiple stable `cargo.*` visual identities;
3. a pure deterministic resolver chooses a visual by level number + archetype ID;
4. cargo tile, warehouse target and travel flight use the same resolved visual;
5. missing/unadmitted runtime images render the existing Flutter fallback;
6. AST-011 provenance/licensing remains mandatory before a real WebP can be admitted.

## Production intake checkpoint

The next executable step is now deterministic and source-controlled rather than a manual 124-item checklist:

- `GameAssetIntakePlan` classifies each cargo descriptor as admitted, missing binary, missing provenance, or missing both.
- Partial admissions are prioritized before untouched assets so an interrupted art batch is repaired before new work starts.
- Runtime paths are normalized for Windows/Linux consistency.
- Any registered provenance record is validated against the matching manifest descriptor before it can appear as ready.
- `tool/plan_ast_007_asset_intake.dart` emits the next production batch (default 12, configurable up to 124) with stable ID, concept, exact runtime path, profile and dimensions.
- `--json` output is available for automation or handoff to an art-generation/import pipeline.
- The planner does not invent or auto-approve provenance. Real WebP and commercial-use evidence remain mandatory through AST-011.
